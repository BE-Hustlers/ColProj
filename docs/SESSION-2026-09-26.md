# Session log — 26 September 2026

Everything built, every decision taken, and the reasoning behind each one.
Written as a record so that in three weeks nobody has to reconstruct why the
code looks the way it does.

Project review: **1 October 2026**. APK target: **Monday 28 September**.

## 1. What we set out to do

Build a standalone Android application that marks classroom attendance from a
photograph, running entirely on the handset, with no server. It has to work as
an independent app now and slot into the college ERP later. Four-tier staff
hierarchy, timetable-driven class selection, face recognition against a
per-class student database, manual fallback, and a correction mechanism that
teaches the system.

Session goal: get a working, demonstrable build in one sitting.

**Outcome: done.** Full application, 79 passing tests, single-file build,
Capacitor-ready project, three documents.

---

## 2. Questions asked before writing code, and what they changed

Seven questions were put before anything was built. Five of them changed the
design.

**Face resolution in group shots.** ArcFace needs a 112×112 aligned crop.
In one wide photo of a sixty-seat room, back-row faces land at 20–40 px, and
embeddings from upscaled 25 px crops stop separating reliably. This is the
failure mode most classroom-attendance projects hit without planning for it.

→ Produced two features: **column-by-column capture** as the default workflow
(three overlapping shots merged into one attendance event, deduplicated), and a
**minimum face-size floor** (`minFacePx`, default 26) below which a detection
is shown but never auto-matched.

**Which error is preferable.** Asked whether a wrongly-present student or a
wrongly-absent one is worse. Answer: wrongly-absent, because it can be
corrected and the correction feeds the database — the beard/clean-shave case.

→ This is the single decision that shapes the whole matcher. It commits to a
**high threshold and a conservative policy**: three outcomes rather than two,
erring toward Check. It also means demo-day numbers should be presented as
"94% auto-marked, 6% sent for review" rather than "99% accurate".

**Gallery poisoning.** Raised that runtime corrections can destroy the
database: a teacher taps the wrong row, one student's face is written into
another's profile, and the app confidently confuses them from then on. The
reply was that fine-tuning the model should prevent this.

→ It does not — the two are different failure modes. Fine-tuning improves
general discrimination before deployment; poisoning is an operator error at
runtime, after deployment. No amount of pre-deployment tuning stops a
mis-click. The response was to build the dispute loop with four safeguards
(§6.6) rather than to argue the point further.

**Data protection.** Raised DPDP 2023 and consent. Position taken: for a demo
using friends' photos with their agreement, this is genuinely fine and not
worth re-litigating. For real student data it is a prerequisite, and raising it
voluntarily at the review reads as thoroughness rather than as an admission.
Recorded in the README's "explicitly not done" section and left there.

**SHA-256 for passwords.** The original brief said "SHA-256 and MFA
authentication grade". A bare SHA-256 digest is GPU-brute-forceable at billions
of guesses per second and is a weakness, not a feature.

→ Passwords use **PBKDF2-SHA256 at 210,000 iterations** with a per-account
salt. SHA-256 is used where a digest genuinely belongs: the audit chain and the
per-roll seal. Worth being precise about at the review, because a reviewer will
ask which one is meant.

**Spoofing.** Declared out of scope by agreement. The teacher takes the photo,
which removes the usual attack. A printed face on a stick would still work, and
the honest thing is to say so first.

**Timetable binding.** Recommended binding to server time and a registered
device rather than the phone's clock, or a teacher can change their clock and
mark a class that has not happened.

→ All time reads go through a single `Clock` object, which is the one seam the
ERP build substitutes.

## 3. The constraint that reshaped delivery

**No `.apk` could be compiled in this session.** No Android SDK in the build
environment, and Google's Maven and SDK hosts were unreachable, so Gradle
cannot run.

Rather than lose the session to that, the app was built as a complete
phone-installable web application — camera, on-device inference, local storage,
offline — with a Capacitor config and three commands that wrap it into a signed
APK locally in about twenty minutes. Not a line of the app changes in that step.

Two related sandbox limits also mattered:

- **Published-artifact sandboxes block fetches to model CDNs**, so the shared
  single-file build cannot load ONNX weights.
- **Google Drive was unreachable**, which is where every public RetinaFace
  weight file lives.

Both fed directly into the engine architecture and the detector choice.

## 4. Model selection, and the substitution to defend

### What was tried

Downloaded InsightFace `buffalo_sc` (15 MB) successfully. Probed four separate
GitHub repositories for a RetinaFace ONNX export. Results: two 404s, one
134-byte Git LFS pointer, and one repository shipping SCRFD rather than
RetinaFace. Every genuine RetinaFace weight file is on Google Drive.
`antelopev2` was reachable but is 360 MB — irrelevant for a phone.

### What was chosen

| Role | Model | Size |
|---|---|---|
| Detector | SCRFD-500M (`det_500m.onnx`) | 2.5 MB |
| Recogniser | ArcFace MobileFaceNet, WebFace600K (`w600k_mbf.onnx`) | 13.6 MB |

The recogniser is genuine ArcFace — ArcFace loss, 512-d output. Only the
detector was substituted.

### Why this is defensible

SCRFD is by the same InsightFace authors as RetinaFace, is its direct
successor, and beats it on WIDER FACE at a fraction of the compute. The
RetinaFace ResNet50 variant is over 100 MB and is not shippable in a phone app.

To keep the option open, `OnnxEngine._decodeRetina` implements the full
RetinaFace prior-box decode (steps 8/16/32, min sizes
`[[16,32],[64,128],[256,512]]`, variances `[0.1,0.2]`) and `DETECTORS.retinaface`
holds its configuration. Dropping `retinaface_mnet025.onnx` into `models/` and
setting `detector: 'retinaface'` switches it. **That path has never been
executed** — there were no weights to test it with — and it is labelled
unverified in `docs/CONTEXT.md` rather than quietly presented as working.

**Framing for the review:** *we evaluated RetinaFace and selected its successor
for mobile viability.* That is a stronger answer than the original claim, but
it changes a slide, so decide before Wednesday whether to use it.

## 5. Validation done before any application code was written

Building the app first and hoping the inference is right is how these projects
fail quietly. The pipeline was proven in Python first.

### Pipeline correctness

A reference implementation (`ref_pipeline.py`, used in the build environment,
not shipped) ran the full path — letterbox, SCRFD decode, 5-point alignment,
ArcFace embedding — on a real photograph.

```
faces: 1    box 1052,470,1688,1479    detection score 0.808
embedding shape (1, 512)              L2-norm 1.0
```

The aligned 112×112 crop was inspected visually: eyes level and centred, the
standard ArcFace framing.

### Embedding robustness

The measurement that mattered, because it predicts back-row behaviour:

| Perturbation | Cosine against original |
|---|---|
| Horizontal flip | 0.948 |
| 50% brightness | 0.957 |
| 8× downscale then upscale | 0.977 |

Impostor pairs on this model typically sit at 0.0–0.2, so the separation margin
is wide. This is what justified an accept threshold of **0.45** with a review
band beneath it.

### Alignment maths

Umeyama alignment normally needs an SVD, which is unpleasant in JavaScript. A
closed-form least-squares similarity transform (scale + rotation + translation,
no reflection) was checked against Umeyama over 500 random landmark sets:

```
max absolute difference: 3.0e-5     (float32 noise)
```

So no SVD in the JS port. This is verified, not assumed, and should not be
"improved" later.

## 6. What was built, and the reasoning inside it

### 6.1 Three interchangeable engines

The published-artifact sandbox cannot load model weights, and the team wanted
demo mode to be modular for UAT rather than a scripted path. Both needs are met
by the same design: one interface, three implementations.

| Engine | What it is | When |
|---|---|---|
| `onnx` | Real SCRFD + ArcFace | Weight files present |
| `synthetic` | Simulator, no weights | Fallback, threshold work |
| `fixture` | Replays a recorded run | Repeatable UAT |

The app probes for weights at boot and picks automatically, with a manual
override in the UAT panel. Nothing else in the application branches on which
engine is running. The same build therefore demonstrates on a laptop with no
models, on a phone with models, and inside the APK.

**The simulator is not a mock.** Each identity is a deterministic 512-d unit
vector; a capture perturbs it with Gaussian noise. Measured over 300 identities
(44,850 pairs):

| Property | Measured | Theory |
|---|---|---|
| Impostor mean | −0.0000 | 0 |
| Impostor sd | 0.0441 | 1/√512 = 0.0442 |
| Max impostor | 0.1997 | — |
| Genuine at σ=0.030 | 0.827 | 0.827 |
| Genuine at σ=0.055 | 0.626 | 0.626 |
| Genuine at σ=0.090 | 0.440 | 0.441 |

`cos ≈ 1/√(1 + 512σ²)`. Because the separation geometry matches real ArcFace,
thresholds tuned on the simulator transfer meaningfully. This is worth saying
out loud at the review — it is the difference between a demo and a fake.

### 6.2 Three outcomes, not two

A face is marked present only when it clears the accept threshold **and** beats
the runner-up identity by a margin. Everything else goes to **Check**.
Unresolved rows are saved as absent **and flagged**, never silently dropped.

Defaults: accept 0.45, review 0.32, margin 0.04, minFacePx 26, detScore 0.45.

Tested: 400 off-roll faces produced **zero** false presents.

### 6.3 Per-class matching

A capture is matched only against the enrolled students of that class, never
the whole college. With a 5,000-student flat gallery this would be a different
and much worse retrieval problem.

### 6.4 The timetable gate

A roster unseals only when teacher identity, a registered handset, and the
clock all agree with a scheduled slot. Failures return human-readable reasons
rather than a generic refusal. Overrides are allowed, require a typed reason,
and are written to the audit log with the teacher's name and handset.

All time reads go through `Clock`. That is the ERP seam.

### 6.5 Security

- **Passwords**: PBKDF2-SHA256, 210,000 iterations, per-account salt.
- **Two-step**: real RFC 6238 TOTP. Both published test vectors pass
  (T=59 → `94287082`, T=1111111109 → `07081804`), so the codes validate in
  Google Authenticator. Not simulated.
- **Audit chain**: each entry hashes the previous hash plus its own contents.
  Tested to detect an edited entry and name the exact break point.
- **Session seal**: SHA-256 over the full roll. Tested to detect a single
  flipped mark.

This does not make records unchangeable — anyone with the device can change the
data. It makes changes **impossible to hide**, which is the achievable property.

### 6.6 The dispute loop

The team's ART-style idea — a verification list that grows as the system is
corrected — implemented with the safeguards that were missing from the original
sketch:

1. The face crop is shown beside the student's name before anything is written.
2. Every addition records who approved it, when, and in which session.
3. Every added face is individually removable; attendance already recorded is
   unaffected.
4. Templates are capped at eight per student; the oldest *learned* one retires
   first, and enrolment templates are never evicted.

A size warning appears if the face is below the floor, because adding a blurry
face makes future matching worse rather than better.

### 6.7 Interface

Built as an attendance register rather than a dashboard: ruled rows, roll
numbers in a fixed left gutter, tabular figures so they align. Deliberately not
a card-grid, because the roster *is* the product and a register is the
vernacular the users already know.

Practical constraints drove the rest. It is used standing up, one-handed, in a
classroom, sometimes in glare — so large touch targets, primary actions
bottom-anchored in the thumb zone, and state shown by glyph and text as well as
colour. System fonts rather than a web font, because the APK must work offline.

Guided walkthrough overlays on first use, as asked, dismissible and replayable
from Settings.

## 7. Bugs found by the tests

Three real bugs, all caught before the app was ever opened in a browser. This
is the argument for having written the tests.

**Simulator attendance was re-rolled per shot.** Across three shots the union
included almost everyone, so nobody ever came out absent — the output was "57
present, 0 absent", which looks like success and is actually a broken
simulation. Who is in the room is now fixed per session; only visibility varies
per shot. Output became a realistic 27 present / 17 to check / 13 absent.

**Capture noise ignored row depth.** Added `_noise = σ·(1 + 2.1·(1−depth))`, so
back rows degrade. This is what produces the unplaced faces that make the
correction workflow demonstrable, and it is physically faithful — the real
model measurements in §5 show the same effect.

**`analyse` crashed if the view changed mid-run.** It assumed its DOM nodes
still existed. Null-guarded in both the capture and enrolment paths.

Two further issues were test-harness gaps rather than app bugs, both now fixed
and documented because each cost time:

- Top-level `const`/`class` in a classic `<script>` never become `window`
  properties, though sibling scripts can reference them. Harnesses need a
  bridge script.
- jsdom does not expose `TextEncoder`. Without a shim, `core.js` aborts at its
  first use and the failure surfaces far away as "Settings is undefined". The
  harness now also attaches a `jsdomError` listener so script errors are
  reported where they happen.

One "failure" was the test being wrong, not the code: at σ=0.075 the simulated
cosine is 0.461, legitimately above the 0.45 accept line. Useful calibration
fact — the accept threshold corresponds to σ ≈ 0.088.

## 8. Test coverage

79 tests, three suites, no browser required. `npm test`.

- **`logic.test.mjs`** (21) — alignment against Umeyama, simulator statistics
  against theory, matcher bands, RFC 6238 vectors, PBKDF2.
- **`flow.test.mjs`** (52) — boots the real app under jsdom and drives it end
  to end: sign in, role scoping across all four levels, timetable gate
  including the unregistered-handset refusal, capture, analyse, correct a face,
  verify the correction is matched next time, undo it, save, verify the seal,
  tamper with the audit log and detect it, render every view.
- **`dist.test.mjs`** (6) — boots the built single file and signs in, proving
  the build output works rather than just the sources.

**Untested**: real ONNX inference in a browser, actual camera capture, visual
layout, the RetinaFace decode path, Capacitor/Android behaviour. There is no
browser in the build environment, so no screenshot-level verification exists
and visual bugs have not been ruled out.

## 11. Things to say, and not say, at the review

**Say:**
- The detector is RetinaFace's successor, chosen for mobile viability, and the
  RetinaFace path is implemented behind a config flag.
- Three outcomes, not two, and why: a wrongly-absent student is corrected in
  seconds, a wrongly-present one is undetectable fraud.
- The simulator's separation geometry matches real ArcFace, with the measured
  numbers to back it.
- Corrections require human confirmation and are reversible, because gallery
  poisoning is a runtime error that fine-tuning cannot prevent.
- What is deliberately not done: liveness, consent workflow, ERP. Volunteering
  the gaps is stronger than being caught by them.

**Do not say:**
- "SHA-256 password hashing." It is PBKDF2. The distinction is the point.
- "99% accurate." Quote auto-marked share and false-present count separately.
- That the RetinaFace path is tested. It is written and unverified.
